# Bybit Options Bot — план и контекст

Управление торговлей опционами Bybit (API V5, `category=option`) через скрипт и Telegram-бот.
Запуск — на VPS пользователя. Язык общения с пользователем — русский.

## Требования
- Базовые активы: BTC, ETH, SOL (USDT-settled опционы, символы вида `BTC-27MAR26-70000-P-USDT`).
  Список задаётся в `.env` (`BASE_COINS`), расширяемый.
- Аккаунт: UTA. Для бота — отдельные новые API-ключи (права: Contract/Options Trade + Read — проверено 2026-11-16
  на demo-ключе: Options, ContractTrade, Derivatives, Spot; Wallet пусто. Бот торгует только опционами (код), спот
  в ключе mainnet не включать;
  БЕЗ вывода средств, привязка к IP VPS).
- Разработка и проверки — сначала на testnet (`BYBIT_ENV=testnet`), mainnet — только после явного согласия пользователя.
- Безопасность: доступ по ролям (см. «Telegram: доступ»); каждый ордер подтверждается кнопкой;
  локальные лимиты `MAX_QTY_<COIN>` и `MAX_ORDER_PREMIUM_USDT` проверяются до отправки.

## Готово
- `optbot/config.py` — настройки из `.env`.
- `optbot/bybit_client.py` — `OptionsClient`:
  инструменты (кеш 5 мин), `expiries`, `resolve_symbol` (принимает короткие формы),
  `chain` (страйки вокруг ATM с котировками и греками), `ticker`,
  `balance`, `positions`, `open_orders`, `greeks`,
  `prepare_order` (округление по шагам + лимиты, без отправки), `place_order` (по цене / по IV / market,
  `orderLinkId` генерируется — для опционов обязателен), `cancel_order`, `cancel_all`,
  `close_position_request` (reduce-only на весь размер).
- Smoke-тесты на `BYBIT_ENV=demo` пройдены (2026-11-15): справочник, экспирации, цепочка, баланс,
  лимитный ордер далеко от рынка → отмена (`smoke.py`, `smoke_order.py`).
  Сверены реальные поля: tickers — `bid1Price/ask1Price/bid1Iv/ask1Iv/markPrice/markIv/delta/gamma/vega/theta/
  underlyingPrice/openInterest`; open orders возвращают `orderIv` и для ценовых ордеров.
  Исправлено: `prepare_order` брал `askPrice/bidPrice` (таких полей нет) → оценка премии market/IV-ордеров
  молча шла по markPrice; теперь `ask1Price/bid1Price`. Кеш инструментов защищён `RLock` (бот зовёт из потоков).
  Исполняемые ордера на demo (2026-11-15): покупка 0.01 BTC-пута и продажа 1 SOL-колла (исполнены по лучшей
  цене стакана), закрытие через `close` — BTC лимиткой, SOL по рынку; позиции обнулились.
  Сверены поля `positions`: `side` Buy/Sell, `size` без знака, `avgPrice`, `markPrice`, `unrealisedPnl`,
  греки уже на всю позицию (со знаком); `get_coin_greeks`: `totalDelta/Gamma/Vega/Theta`.
- Изменение ордера: `amend_request` (берёт недостающее из открытого ордера, проверяет лимиты) + `amend_order`;
  CLI `amend SYMBOL ID [--price|--iv] [--qty]`, бот `/amend SYMBOL ID PRICE|ivNN [QTY]` с подтверждением.
  Проверено на demo.
- `optbot/fmt.py` — общее форматирование (CLI и бот): цепочка компактная (телефон) и `--wide`,
  тикер, баланс, позиции, ордера, греки, превью ордера с рынком и премией; `parse_iv`, `to_dec`.
- `optbot/cli.py` — `python -m optbot.cli …`: `expiries`, `chain BASE EXP [-n N] [--wide]`, `ticker`, `balance`,
  `positions`, `orders`, `greeks`, `buy/sell SYMBOL QTY (--price|--iv|--market) [--tif] [--reduce-only]`,
  `cancel SYMBOL ID`, `cancel-all [BASE]`, `close SYMBOL [--price]`. Все торговые действия — с превью и y/N.
  Проверено на demo: чтение, лимиты, ордер по цене и по IV далеко от рынка → cancel / cancel-all.
- `optbot/bot.py` — `python -m optbot.bot` (PTB v22 + `[rate-limiter]`, pybit через `asyncio.to_thread`):
  /id, /exp, /chain (актив и экспирация кнопками, «Обновить» правит то же сообщение), /t, /bal, /pos,
  /orders (кнопки отмены — только трейдерам), /greeks, /buy и /sell (`PRICE | ivNN | mkt`), /close,
  /cancel, /cancelall. Проверено обработчиками с подставным Telegram против demo, включая группы
  (ордер далеко от рынка → подтверждение инициатором → отмена кнопкой, уведомления в группы).
  В живом Telegram ещё не запускался — в `.env` пусты токен и списки id.

## Telegram: доступ (реализовано)
- Работает в личке и в группах из `TELEGRAM_ALLOWED_CHAT_IDS` (id отрицательные). В любом другом чате
  бот не отвечает и выходит (`TypeHandler` в group=-1 до всех обработчиков); id чата пишется в лог WARNING —
  так узнаётся id новой группы.
- Права по `from_user.id`: `TELEGRAM_TRADER_IDS` — торговля+просмотр, `TELEGRAM_VIEWER_IDS` — просмотр,
  `ALLOW_ALL_GROUP_MEMBERS_VIEW` (false) — просмотр всем в разрешённых группах (в личке не действует).
  Неразрешённым — молчание; зрителю на торговую команду — «Нет прав».
- Сообщения с `sender_chat` (анонимные админы, каналы) и служебные id Telegram к торговле не допускаются.
- `/id` — всем (в личке и разрешённых группах): user id, chat id, роль. `/start` незнакомцу в личке — его id.
- `SENSITIVE_COMMANDS_DM_ONLY` (по умолчанию true): /bal, /pos, /orders, /greeks в группах отвечают
  «только в личке».
- Подтверждение ордера/close/cancel-all: нажать может только инициатор, TTL 60 с, повтор нажатия не шлёт дважды.
- Аудит: логгер `optbot.trade` — `<event>.request/confirm/done/error/expired/cancelled_by_user`, `denied`,
  `rejected`, всё с user id и chat id.
- Уведомления о выполненных действиях (ордер принят, отмена, cancel-all) — во все разрешённые группы,
  кроме исходной. Исполнения (fills) пока не отслеживаются — нужен WebSocket (п. «Потом»).
- Лимиты Telegram: `AIORateLimiter(max_retries=3)` (30/с всего, 20/мин на группу, ожидание RetryAfter),
  навигация кнопками правит сообщения, уведомления шлются фоновой задачей.
- Старт запрещён, если нет токена, никому не выдан доступ, в `TELEGRAM_ALLOWED_CHAT_IDS` положительный id
  или в списках пользователей служебные id. Старая переменная `TELEGRAM_ALLOWED_IDS` больше не используется.

## Защита, кнопки, исполнения (реализовано 2026-11-15)
- `prepare_order` (клиент), всё проверяется и при превью, и повторно при отправке:
  - стакан: для market — есть встречные заявки, спред ≤ `MAX_SPREAD_PCT` (20), хватает глубины (25 уровней);
    для пересекающих рынок лимиток и market — худшая цена исполнения хуже mark не более `MAX_SLIPPAGE_PCT` (15).
    Пассивные лимитки (не пересекают рынок) не ограничиваются. Ордера по IV — без проверки стакана.
  - портфель (не для reduce-only; уменьшать можно всегда): `MAX_POSITION_<COIN>` — |позиция| по символу
    с учётом открытых ордеров в ту же сторону; `MAX_NET_DELTA_<COIN>` — |дельта опционов| по активу (get_coin_greeks
    + qty×delta тикера); `MAX_DAILY_PREMIUM_USDT` — с начала суток UTC: cumExecValue + остаток активных ордеров,
    все опционные не-reduce-only ордера счёта (не только бота). При amend изменяемый ордер исключается.
  - цена округляется к шагу в пассивную сторону (покупка вниз, продажа вверх).
  - превью показывает оценку исполнения и состояние лимитов (`OrderRequest.info`).
- Бот: `/orders` — кнопки «✏ Изменить» (меню bid/mid/ask/mark или «Своя цена / кол-во…» ответом на
  ForceReply) и «✖ Отменить»; `/pos` — «Закрыть · рынок» / «· mid». Данные кнопок — короткие токены
  в памяти (30 мин), меню изменения нажимает только тот, кто его открыл.
- `optbot/ws.py` — приватный WebSocket (pybit, demo/testnet/mainnet), поток execution по опционам →
  «💥 Исполнение» во все разрешённые группы и трейдерам в личку (если начинали диалог с ботом);
  сделки вне бота тоже видны; аудит `exec` в `optbot.trade`.
- Проверено на demo: отказы по лимитам, проскальзыванию, спреду; глубина — на подставном стакане;
  кнопки и меню — подставным Telegram; WS — живыми сделками 0.01 BTC-пута.
- `.env` — права 600; git-репозиторий создан (без коммитов). `SENSITIVE_COMMANDS_DM_ONLY=false` на время тестов.

## Исправления по код-ревью (2026-11-15)
- Лимитная цена сама сравнивается с mark (`_check_limit_price`): покупка дороже / продажа дешевле mark больше
  чем на MAX_SLIPPAGE_PCT — отказ (раньше проверялись только уровни стакана, остаток мог встать по абсурдной цене).
- Премия market-ордера для MAX_ORDER_PREMIUM_USDT — по стоимости прохода по стакану, а не лучшая цена × qty.
- `close_position_request`: цена 0 → отказ (раньше молча превращалась в market); кнопка «· mid» без котировок — отказ.
- `BybitNetworkError` (таймаут, обрыв, HTTP-ошибка) отделён от `BybitError` (отказ биржи). После сбоя бот/CLI
  ищут ордер по `orderLinkId` (`find_order_by_link`) и сообщают фактический статус; любые иные исключения при
  отправке тоже фиксируются в аудите, сообщение не зависает на «Отправка…».
- Уведомления в личку отключаются только при Forbidden / chat not found, не при временных сбоях.
- `smoke_order.py`: запрет на mainnet, устойчивый выбор инструмента, цена ~10% от mark, отмена в finally.
- amend частично исполненного ордера: в лимитах позиции/дельты/премии учитывается только остаток (qty − cumExecQty);
  новое qty должно быть больше исполненного.
- Тикер из `prepare_order` переиспользуется в превью; open_orders запрашивается один раз за проверку;
  брошенные вопросы «Своя цена…» очищаются вместе с устаревшими токенами.
- Второй раунд ревью: после сбоя связи статус ищется с повторами (~15 с) и никогда не утверждается «не выставлен»;
  закрывающая лимитка сверяется с лучшей встречной котировкой, а не с mark (можно закрыться по mid на широком спреде);
  локальные ошибки (нет ключей, неверные параметры) — не «сбой связи»; amend перепроверяет исполненную часть при
  подтверждении и после округления qty; поздний ответ на «Своя цена…» → «Меню устарело»; CLI amend/сбой поиска.
- Третий–пятый раунды ревью: retCode 10000/10016/10019 = статус неизвестен; BYBIT_ENV только testnet/demo/mainnet;
  поиск ордера по orderId (биржа при этом ИГНОРИРУЕТ symbol — символ сверяется отдельно), статус Created активен;
  пустой amend отклоняется; общий опрос статуса с повторами для ордера, amend и отмен.
- Известные ограничения: суточная премия считается по дню СОЗДАНИЯ ордера (исполнения сегодня по вчерашнему ордеру
  не входят) — точный учёт по исполнениям после журнала сделок (этап 2).
- Не сделано (низкий приоритет): фильтр settle coin для USDC (отложено). Пагинация open_orders/positions — сделана.
- Трейдеры: 205102580 (Павел), 1470678444, 442293623 (Natali, создатель группы).

## Логи: сбои Telegram (2026-11-17)
`502 Bad Gateway` / таймауты опроса `getUpdates` — сбой на стороне Telegram, библиотека сама повторяет запрос,
сообщения не теряются (Telegram хранит их до 24 ч). `on_error` пишет такие ошибки одной строкой WARNING без
трейсбека (только ошибки самого опроса); серия (паузы ≤ 2 мин) дольше 5 мин — строка ERROR «Telegram недоступен
уже N мин» раз в 5 мин. Таймауты опроса библиотека повторяет молча (в `on_error` не попадают) — долгий сбой из одних
таймаутов в логе не виден; конец сбоя — по последней строке WARNING. Сетевые ошибки команд, кнопок и задач
(их никто не повторяет), `BadRequest` и прочее — ERROR с трейсбеком и update.

### Этап 1. Сборщик данных `optbot/collector.py` — реализовано 2026-11-15
Сделано: `optbot/db.py` (WAL, миграции через user_version), таблицы snapshots / spot / tracked_symbols / leg_marks,
задача JobQueue в боте (выравнивание по слоту, `COLLECTOR_ENABLED`, `COLLECTOR_INTERVAL_MIN`, `DB_PATH`),
CLI `python -m optbot.collector --once|--stats`, тесты `tests/test_collector.py`. Проверено на demo: ATM IV и RR25
сверены с сырыми тикерами. Индекс берётся из indexPrice опционов, перпетуал — markPrice BASEUSDT.
Начать первым: IV percentile и оценка сигналов требуют накопленной истории (недели).
1. Каждые 15 мин (выравнивание по :00/:15/:30/:45) для каждого BASE и каждой экспирации, взятой из get_tickers по baseCoin:
   - цена базового актива (`underlyingPrice` и индекс), время до экспирации;
   - ATM-страйк (ближайший к форварду), ATM IV (среднее markIv колла и пута);
   - цена ATM-стрэддла (mark и mid по bid/ask);
   - 25-дельтовый risk reversal: IV колла с delta ≈ +0.25 минус IV пута с delta ≈ −0.25,
     с линейной интерполяцией по дельте между соседними страйками;

2. Таблицы:
   - `snapshots` (ts, base, expiry, dte, underlying, atm_strike, atm_iv, straddle_mark, straddle_mid, rr25,
     iv_c25, iv_p25, atm_spread_pct, atm_oi);
   - `spot` (ts, base, index_price, perp_price).
   - Ключ (ts, base, expiry), повторная запись игнорируется.
3. Слежение за ногами активных сигналов (нужно этапу 4): mark, bid и ask конкретных символов из таблицы `tracked_symbols`.

### Этап 2. Журнал сделок — реализовано 2026-11-15
Сделано: `optbot/journal.py`, `optbot/linkid.py`, миграция 2 в `db.py`, WS-топик `order`, сверка при старте и каждый час
(`JOURNAL_SYNC_MIN`), сводное уведомление о пропущенном WebSocket, `/journal [период] [csv]`,
CLI `python -m optbot.journal --sync | --report ПЕРИОД [--csv]`, тесты `tests/test_journal.py`.
Проверено на demo: выгрузка 30 дней (11 исполнений, 28 ордеров, 150 цен поставки); PnL сверен с ручным расчётом;
живая покупка через CLI записана из WS с источником cli; продажа при выключенном боте догружена сверкой
при старте (source=sync), дублей нет, сводка ушла в группу.
Отличия от плана ниже: «кто выставил» — отдельная таблица `order_links` (пишется до отправки, ключ link_id),
`orders` — только состояние ордера с биржи; ручные ордера CLI — `man-u000000-…` с source=cli.
Уведомления: у исполнения флаг `notified`; объявляет кто-то один — WS (подробно) или сводка сверки (только
старше 2 мин; исполнения раньше самой первой сверки (`sync_state` `executions:history_until`) — история
без сводки, даже если первая выгрузка прервалась; `--sync` из CLI сводку не «съедает»). Запись из WS — не в потоке
pybit. Поставка закрывает позицию по внутренней стоимости (цена — из delivery-record или new-delivery-price);
без цены — позиция закрыта, PnL не учтён, в отчёте предупреждение.
Отклонённый лимитами или биржей ордер удаляет свою запись из `order_links` (при сбое связи — остаётся).
`order/history` окном видит ордер только по времени создания (сверено на demo) — сверка дочитывает активные
по журналу ордера по `orderId` (до 100 за проход). Сводка о пропущенных, не доставленная ни в один чат, повторяется
следующей сверкой.
**Известные ограничения:** (1) позиция, открытая раньше выгрузки (30 дней), неизвестна журналу: её закрытие
сделкой выглядит как открытие встречной позиции (фантом в «Открыто», ложный PnL при её поставке). Для перехода

### Этап 3. Сигналы `optbot/signals.py` и `/signals <BASE>` — реализовано 2026-11-16
Сделано: `/signals [BASE]` в боте (кнопки активов, «Обновить» в том же сообщении), `cli signals BASE`,
пороги `SIG_*` (`config.SignalSettings`, перепутанные пары — по умолчанию). Цены ног — по исполнимой стороне,
рядом mid; количество — минимальный лот; риск/прибыль/безубыток — общей функцией выплаты (`signals.profile`).
Экспирации короче суток в IV7 не участвуют. IV percentile — по IV7 каждого среза сборщика; «достаточно истории» —
по часам со срезами (пропуски не в счёт), последний срез старше 6 ч — «история устарела», только IV/RV. RV — только по соседним часовым свечам. Неликвидный страйк заменяется
соседним с близкой дельтой (у SOL OI мал — без этого ноги не проходили `SIG_MIN_OI_USD`). Стрэддл — не дороже
справедливой цены по RV7 (≈0.8·S·RV7·√t). Кэш карточки 30 с на актив (повтор — «Без изменений»), одновременные нажатия — один расчёт. IV7 истории
кэшируется (из БД дочитываются только новые срезы); тикеры, справочник и свечи грузятся параллельно.
1. Метрики:
   - IV на фиксированный срок 7 дней: интерполяция ATM IV по полной дисперсии (σ²·t) между соседними экспирациями;
   - реализованная волатильность за 7 и 14 дней по часовым свечам перпетуала (`/v5/market/kline`, linear,
     `BTCUSDT` и т.д., interval=60), годовая;
   - IV percentile 7d по истории сборщика (пока истории мало, ниже `MIN_HISTORY_DAYS`, — помечать «мало истории»
     и опираться на IV/RV);
   - ожидаемое движение до экспирации: S·IV·√t и цена ATM-стрэддла;
   - тренд: EMA(fast/slow) на 4h-свечах и наклон;
   - фильтры ликвидности: спред ≤ X%, OI ≥ Y, ненулевой bid по каждой ноге, минимальная премия.
2. Таблица выбора стратегии (только ограниченный риск; пороги в config):
   - IV высокая (pctl ≥ hi, IV7 > RV7·k) и тренда нет → железный кондор: короткие ноги ≈ ожидаемое движение
     или |Δ| ≈ 0.15–0.20, крылья на заданной ширине;
   - IV высокая и тренд вверх / вниз → кредитный спред пут / колл (бычий / медвежий);
   - IV низкая (pctl ≤ lo или IV7 < RV7) и тренд есть → дебетовый спред по тренду;
   - IV низкая и тренда нет, IV7 < RV7 → длинный стрэддл (риск = премия);
   - иначе → «сигнала нет» с объяснением.
3. Подбор: экспирация в окне 2–7 дней (лучшая по ликвидности и близости к 7d), страйки по дельте или ожидаемому
   движению с учётом шага страйков и ширины крыльев по активу, проверка ликвидности каждой ноги.
4. Карточка `/signals <BASE>`: стратегия и ноги (символ, сторона, кол-во, цена), премия (кредит или дебет),
   максимальный риск, максимальная прибыль, точки безубытка, суммарные греки, причина (метрики и сработавшие пороги),
   свежесть данных. Кнопка «Выставить» — этап 5.
5. Все пороги в `config.py` / `.env` (SIG_*). Юнит-тесты расчётов: интерполяция IV, RV, выплата стратегий.

## Несколько счетов: сервис данных и экземпляры бота (решено 2026-11-27, не реализовано)
Цель: функции бота нужны не только на demo, но и для управления реальными счетами. Разные счета — с разным набором
функций: demo — эксперименты и (в будущем) автоторговля, реальный счёт — инструмент для ручных сделок трейдеров и
анализа. Конечная цель — автоторговля и на реальных деньгах (только после отдельного решения пользователя).

**Схема: один экземпляр бота — один счёт.** У каждого экземпляра свой каталог, `.env` (ключ API, лимиты `MAX_*`,
суточная премия), Telegram-токен, люди и группы, своя БД счёта и служба `systemctl --user`. Ключи и лимиты разных
счетов не смешиваются ни в одном процессе — ордер «не на тот счёт» невозможен по построению. Мультисчёт в одном
процессе (колонка счёта во всех таблицах журнала, выбор счёта в каждой команде) — отклонён.

**Доступ (заменяет правило E2 п. 0):**
- в группе экземпляра все участники видят всё — карточки, `/books`, `/stress`, данные счёта (`/bal`, `/pos`,
  `/orders`, PnL); ордера (в том числе «Выставить», close, cancel-all) — только трейдеры и администратор;
  в личке — по ролям, как сейчас; в настройках это `ALLOW_ALL_GROUP_MEMBERS_VIEW=1`,
  `SENSITIVE_COMMANDS_DM_ONLY=0` у экземпляра реального счёта (данные счёта в `/stress` и `/books` уже следуют
  `SENSITIVE_COMMANDS_DM_ONLY`);
- экземпляр demo — только администратор и только личка (групп нет, чужим — молчание);
- экземпляр реального счёта — работает в группе, ордера выставляют трейдеры и администратор.

**Происхождение ордера** — признак на входе в контур риска (`prepare_order` / `multileg`): `manual` (по команде
человека), `auto` (по инициативе бота — автоторговля), `copy` (повтор сделки с другого счёта, задел — ниже).
- `manual` — разрешён на любом счёте; на реальном счёте перед отправкой — итог сделки и кнопки «Подтвердить» /
  «Отмена»: ноги и текущие цены, премия, максимальный риск, оценка IM, остаток суточного лимита; без подтверждения
  ордер не уходит. Действия внутри ручной сделки (закрытие купленных ног, если короткая не исполнилась) — часть
  `manual`.
- `auto` и `copy` без подтверждения человека — разрешены только на demo. На реальном счёте — ворота: одновременно
  `AUTOTRADE_MAINNET=1` в `.env` и включение администратором (`/autotrade on`, в личку), свои лимиты (дневной убыток,
  малые `MAX_*`); проверка — при старте и перед каждым ордером, иначе отказ и срочное администратору. Пока
  `AUTOTRADE_MAINNET` не включён (отдельное решение пользователя, не раньше январского пересмотра 15.01.2027).
- Тест: `auto` на mainnet при закрытых воротах ни при каких настройках не доходит до `place_order`.

**Сервис рыночных данных `options-market`** (без Telegram, `data/market.db`). Рынок одинаков для всех счетов (demo
торгует на рынке mainnet), поэтому данные собираются один раз:
- в сервис переезжают сборщик (`snapshots`, `chain_snapshots`, `leg_marks`, `spot`, `perp_context`, `fear_greed`),
  свечи и HAR (`perp_h1`, `har_models`), DVOL (`dvol_h1`), ставка FRED, `delivery_prices`;
- у экземпляров — своя БД счёта: журнал сделок (`orders`, `executions`, `deliveries`, `order_links`), сигналы и их
  исполнения, бумажные книги, `bot_state`; `market.db` подключается через `ATTACH` (имена таблиц уникальны — код
  чтения почти не меняется), писать в неё экземпляр может только в `tracked_symbols` (за какими ногами следить:
  позиции, книги, сигналы; WAL, `busy_timeout`);
- шаг бумажных книг — не вызовом после среза в процессе, а по появлению нового среза в `market.db`;
- устаревание: нет свежего среза дольше N минут — экземпляр не строит сигналов и пишет администратору (ручные
  ордера работают); сервис может и сам слать срочные администратору (отправка без `getUpdates` конфликта токена не
  даёт);
- плюсы: одна история и одна нагрузка на API; новый экземпляр сразу видит pctl, HAR и DVOL по всей истории;
  перезапуск бота больше не теряет срезы (правило «не ближе минуты к :00/:15/:30/:45» — только для сервиса данных);
- минус — общая точка отказа (закрывается проверкой устаревания); миграции — две серии (рынок, счёт), обе только
  дописывать; разовый перенос текущей `market-demo.db` на две БД.

**Несколько групп и субсчетов (задел, не делать сейчас).** Возможные случаи:

3. **Автоматические сигналы — администратору в личку** — сделано 2026-11-17 (в группы не идут):
   - ежедневная сводка по BTC/ETH/SOL в фиксированное время (например, 09:00 UTC — после поставки 08:00):
     по каждому активу сигнал (стратегия, ноги, риск) или «сигнала нет: причина» одной строкой;
   - сообщение при смене рекомендации: проверка вместе со сборщиком (каждые 15 мин), пишет, только когда
     стратегия по активу поменялась (нет → есть, есть → другая, есть → нет), не чаще раза в N часов на актив;
   - время сводки и N — настройки; оба вида пишутся в журнал сигналов (source=auto), так статистика копится
     и без ручных /signals.

   «смена» — другая стратегия (или нет ↔ есть), не другие страйки; должна продержаться 2 проверки подряд (один
   срез с широким спредом не даёт «есть → нет → есть»); в журнал — только доставленное (поэтому без номера в
   сообщении) и только тем администраторам, кому дошло; в сообщении о смене нет «Обновить» (стёрло бы «что на
   что»); `/id` показывает «администратор»; проверка смены — отдельной задачей (медленная биржа не задерживает
   сборщик; предыдущая не кончилась — новая пропускается), расчёт по активам параллельно и мимо 30-секундного
   кэша; срез не удался — смену не проверяем; сбой расчёта рвёт серию «подряд»; сводка и проверка — под одной
   блокировкой (в одну минуту не напишут дважды); сменилось внутри паузы — сообщается после паузы, если отличие осталось;
   отсчёт — две одинаковые проверки подряд после старта (состояние в памяти, о смене за время простоя не
   сообщается); сводка — снимок, точку отсчёта и паузу не меняет (сбойный замер в 09:05 не даёт ложной смены).
4. **Срочные уведомления администратору** (решено 2026-11-17, сделано 2026-11-18; дневной лимит убытка — вместе
   с ним в E2) — отдельным сообщением сразу, не дожидаясь отчёта. Реализация: `OptionsBot.admin_alert(key, text)` —
   «тишина» по ключу (`ADMIN_ALERT_QUIET_MIN`, 30 мин; запуск/остановка — без неё); клиент биржи зовёт
   `on_access_error` (retCode `ACCESS_RET_CODES`, HTTP 401/403) и `on_limit` (`LimitError` — лимиты `MAX_*` и
   маржа; `PortfolioLimitError` — по состоянию счёта) из любого потока (`alert_threadsafe`); сделка вне бота — по
   `orderLinkId` (источник `external`, execType Trade) из WebSocket и сверки журнала; запуск — отметка `running`
   в `bot_state` (миграция 5): осталась от прошлого раза — «прошлая остановка была нештатной»; штатная остановка —
   сообщение в `post_stop` (Telegram ещё доступен) и снятие отметки (идущую сделку по сигналу библиотека
   дожидается до `post_stop`; оборвёт её только kill по таймауту остановки — тогда при запуске «нештатная»).
   Срочное, которое никому не дошло, «тишину» не начинает; одновременные с одним ключом — одно сообщение (ключ
   занят до отправки); важные (сделка вне бота, исполнение не полностью, запуск) не дошли — повторы через 1–20 мин
   (на голом цикле: остановку не держат, снимаются в `post_stop`, а их текст уходит в сообщение «остановлен
   штатно»); повтор помечен временем события. Сделки вне бота — без «тишины», пачка WebSocket — одним сообщением. Ограничение: выход `run_polling` по исключению тоже проходит `post_stop` — будет «остановлен
   штатно» (PTB не различает; на практике фатальные ошибки — до `post_init`). HTTP 401/403 — определённый отказ (`BybitError`, не
   «сбой связи»); 403 у pybit — ещё и превышение лимита запросов по IP.
   Защита от опечаток (цена от mark, стакан) — не лимит риска, администратору не пишется.
   - ошибки доступа к бирже (401, 403, регион);
   - срабатывание лимитов риска и дневного лимита убытка;
   - многоногий ордер, исполненный не полностью;
   - позиции, открытые не через бота (например, вручную на бирже);
   - остановка или перезапуск бота (штатная остановка — сообщением при выключении; падение или kill — бот
     сам не успеет: при следующем старте сообщить «запущен, прошлая остановка была нештатной» по отметке в БД;
     долгий простой без старта увидит только внешний монитор — отдельный вопрос).
   Повтор одного и того же — не чаще раза в «тишину» (настройка), чтобы сбой сети не засыпал личку.
